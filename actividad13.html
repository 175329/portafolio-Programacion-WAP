Parcial 2 · Actividad 13

Evaluación de Seguridad Ofensiva — My File Server 1

Máquina objetivoMy File Server: 1 (VulnHub — Armour Infosec)
EntornoLaboratorio VulnHub, red aislada
MateriaProgramación WAP — Mtro. Servando López Contreras
Fecha30 de septiembre de 2026
Elaborado porJuan Pablo Casanova De La Madrid

01 · Resumen ejecutivo

Resultado de la evaluación

Riesgo global CRÍTICO
Tiempo de compromiso total del sistema: menos de 1 hora.

Se realizó una evaluación de seguridad ofensiva (pentesting de caja negra/gris) sobre el servidor de archivos corporativo "My File Server 1", con el objetivo de determinar su nivel real de exposición ante un atacante externo con conectividad a la red interna.

El resultado de la evaluación es crítico: en menos de una hora de trabajo, el equipo logró comprometer completamente el servidor, obteniendo acceso con privilegios de superusuario (root). La cadena de ataque no requirió el uso de exploits sofisticados ni ingeniería social; se basó en una combinación de malas prácticas de configuración —credenciales expuestas en un archivo de texto plano accesible por HTTP, un recurso compartido SMB con escritura anónima habilitada y un kernel Linux desactualizado y vulnerable— que permitieron escalar de un acceso anónimo a control total del sistema.

Hallazgo principal — cadena de compromiso completa:

(1) enumeración anónima de SMB/FTP → (2) credenciales en texto plano vía HTTP (/readme.txt) → (3) acceso FTP con dichas credenciales → (4) inyección de clave pública SSH vía escritura FTP → (5) acceso SSH interactivo sin contraseña → (6) explotación de Dirty COW (CVE-2016-5195) → (7) shell de root y extracción de /root/proof.txt

Recomendación ejecutiva: se recomienda tratar este sistema como comprometido y proceder a su reconstrucción desde una imagen limpia, rotación inmediata de credenciales, actualización del kernel y aplicación de las contramedidas detalladas en la sección de recomendaciones antes de reincorporarlo a producción.

03 · Metodología aplicada

Enfoque estructurado por fases

La evaluación siguió un enfoque estructurado por fases, alineado con marcos de referencia estándar de la industria PTES (Penetration Testing Execution Standard) y OWASP Testing Guide, adaptado al alcance de una máquina de servidor de archivos:

  • Reconocimiento: identificación del host activo en el segmento de red mediante técnicas de descubrimiento pasivo y activo.
  • Enumeración: identificación de servicios, versiones, y configuración de permisos en cada puerto expuesto.
  • Explotación: obtención de un primer punto de apoyo (foothold) aprovechando configuraciones débiles y credenciales expuestas.
  • Escalada de privilegios: elevación de un usuario sin privilegios a root mediante explotación de vulnerabilidad de kernel.
  • Post-explotación: confirmación del impacto mediante extracción de evidencia (flag) desde el directorio protegido del superusuario.
  • Documentación: registro de evidencia técnica, análisis de riesgo (modelo CIA) y elaboración de recomendaciones de remediación.

Herramientas utilizadas: arp-scan, netdiscover, nmap, smbmap, nikto, navegador web, ftp (cliente), ssh-keygen/ssh, searchsploit, gcc, y el exploit público Dirty COW (exploit-db #40616).

04 · Cadena de ataque

De la enumeración anónima a root

  1. Reconocimiento

    Se verificó la interfaz de red del atacante (eth0), confirmando la dirección 192.168.41.129/24 como punto de partida para el barrido de descubrimiento. Con arp-scan -l se identificaron tres hosts activos, entre ellos un host no documentado (192.168.41.128) candidato a objetivo, confirmado después con netdiscover como una máquina virtual VMware.

  2. Enumeración de puertos y servicios

    Se ejecutó un escaneo exhaustivo de todos los puertos TCP con detección de versión y scripts por defecto (nmap -p- -A), revelando una superficie de ataque amplia y varios servicios con configuraciones de riesgo: FTP anónimo escribible, SSH, HTTP, RPC/NFS, SMB con firma deshabilitada y un segundo servicio FTP (ProFTPD).

    PuertoServicioVersión / Detalle

    22/tcpSSHOpenSSH 7.4 (protocolo 2.0)

  3. Enumeración de SMB y servicio web

    Con smbmap se enumeraron los recursos compartidos sin autenticación (sesión NULL), identificando el recurso "smbdata" con permisos de LECTURA y ESCRITURA para cualquier usuario anónimo. El escaneo con nikto sobre el servicio HTTP identificó indexado de directorios, cabeceras de seguridad ausentes, método TRACE activo y la existencia de un archivo /readme.txt potencialmente sensible, el cual expuso una credencial en texto plano ("My Password is rootroot1"), que combinada con el usuario "smbuser" visible en SMB entregó un par de credenciales completo sin necesidad de fuerza bruta.

  4. Explotación — de FTP a SSH interactivo

    Con las credenciales obtenidas (smbuser:rootroot1) se estableció una sesión FTP autenticada. Dado que el servicio SSH estaba expuesto y el usuario tenía acceso de escritura a su propio directorio home vía FTP, se aplicó la técnica de inyección de clave SSH: se generó un par de claves RSA en el equipo atacante y, mediante FTP, se creó el directorio .ssh y se subió la clave pública como authorized_keys dentro de /home/smbuser/, permitiendo una sesión SSH interactiva sin necesidad de contraseña.

  5. Escalada de privilegios — Dirty COW

    La verificación de identidad confirmó un acceso de usuario estándar sin privilegios administrativos (uid=1000). El kernel del sistema (Linux 3.10.0-229.el7) resultó vulnerable a Dirty COW (CVE-2016-5195), una condición de carrera en el subsistema de memoria que permite a un usuario sin privilegios escribir en archivos de solo lectura, incluyendo binarios con bit SUID. El exploit se transfirió sirviéndolo con un servidor HTTP temporal (python3 -m http.server) y se compiló localmente con gcc, sobrescribiendo /usr/bin/passwd y obteniendo una shell interactiva con privilegios de root.

  6. Post-explotación — prueba de impacto

    Como evidencia final del compromiso total del sistema, se accedió al directorio /root y se extrajo el archivo de prueba, confirmando acceso irrestricto a cualquier recurso del servidor.

    ● Flag de compromiso: af52e0163b03cbf7c6dd146351594a43

05 · Análisis de impacto

Modelo CIA y escenario de impacto empresarial

Al alcanzarse privilegios de root, los tres pilares de la seguridad de la información se ven comprometidos en su totalidad:

PilarSeveridadDetalle
ConfidencialidadCRÍTICOAcceso total de lectura a cualquier archivo del servidor, incluyendo configuraciones, credenciales adicionales y datos almacenados en los recursos compartidos (smbdata, NFS).
IntegridadCRÍTICOCapacidad de modificar o eliminar cualquier archivo del sistema (demostrado al sobrescribir /usr/bin/passwd), incluyendo la posibilidad de alterar datos de negocio o instalar persistencia (backdoors).
DisponibilidadALTOUn atacante con acceso root puede detener servicios críticos (FTP, SMB, NFS, SSH, HTTP) o corromper el sistema operativo, provocando interrupción total del servicio de almacenamiento corporativo.

Impacto de negocio: tratándose de un servidor de archivos corporativo, el compromiso implica una exposición directa de información potencialmente sensible de la organización (documentos, credenciales, datos de clientes o empleados), además de constituir un punto de pivote para comprometer otros sistemas del segmento de red interno.

07 · Recomendaciones técnicas

Remediación correctiva y roadmap

Correctivas inmediatas:

  • Eliminar de forma inmediata el archivo /readme.txt (o cualquier archivo que exponga credenciales) del directorio público del servidor web.
  • Rotar todas las credenciales del sistema, en particular la del usuario smbuser, y eliminar la clave pública inyectada (authorized_keys) del servidor comprometido.
  • Actualizar el kernel de CentOS a una versión parcheada contra CVE-2016-5195 (Dirty COW) y establecer un proceso periódico de gestión de parches.
  • Reconstruir el servidor desde una imagen limpia, dado que se confirmó acceso root; no se debe confiar en la integridad del sistema actual.

Correctivas estructurales:

  • Deshabilitar el acceso anónimo en los servicios FTP (vsftpd y ProFTPD) y exigir autenticación fuerte en todos los servicios expuestos.
  • Revisar y restringir los permisos del recurso compartido SMB "smbdata", eliminando el acceso de escritura anónimo y aplicando control de acceso basado en usuarios/grupos.
  • Habilitar la firma de mensajes SMB (message signing) de forma obligatoria para mitigar ataques de tipo relay.
  • Deshabilitar el método HTTP TRACE y aplicar cabeceras de seguridad HTTP (Content-Security-Policy, X-Content-Type-Options, Strict-Transport-Security, Referrer-Policy).
  • Actualizar Apache HTTP Server a una versión soportada y aplicar hardening del servidor web (ocultar banners de versión, desactivar indexado de directorios).
  • Implementar monitoreo de integridad de archivos (FIM) sobre binarios críticos (/usr/bin/passwd, /etc/shadow, /etc/ssh/) y alertas ante modificaciones no autorizadas.
  • Establecer un programa recurrente de pentesting y gestión de vulnerabilidades sobre los activos expuestos.
  • Aplicar el principio de mínimo privilegio y segmentar la red para limitar el movimiento lateral desde un servidor de archivos comprometido.

Roadmap de remediación:

Inmediato (0–7 días)Reconstrucción del servidor, rotación de credenciales y cierre de accesos anónimos.
Corto plazo (2–4 semanas)Actualización de kernel y hardening de servicios expuestos.
Mediano plazo (1–3 meses)Monitoreo de integridad de archivos y segmentación de red.
ContinuoPrograma recurrente de pentesting y gestión de vulnerabilidades.
